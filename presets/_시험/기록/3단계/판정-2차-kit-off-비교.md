# 3단계 판정 2차 — kit-on 과 kit-off 비교 (r03 · r13 · r15, 2026-09-29)

kit-off = 부품·토큰만 받은 앱 (AGENTS.md · 셸 · 정책 · 검사 도구 없음). 세 세션을 동시에 돌렸고 서로의 화면 파일을 연 기록은 없다.

## 같았던 것 — 키트가 없어도 에이전트가 스스로 했다

| 항목 | kit-off |
|---|---|
| 계약 토큰 | 실제 위반 0 (린트에 걸린 63개는 전부 목데이터 문자열) |
| r15 삭제 | 확인 없이 휴지통 + 되돌리기 토스트, 영구 삭제만 확인창 — **정책 카드와 같은 판단** |
| r03 삭제 | 딸린 계약·메모를 적은 확인창 — 되돌릴 수 없음을 알린다 |
| 성공 알림 | 세 화면 모두 토스트 |
| 화면 품질 | 사진으로는 kit-on 과 비슷하거나 더 풍부하다 (r15 는 처음부터 폴더를 골라 둔 상태로 연다) |

## 달랐던 것 — 키트가 만든 차이

| 항목 | kit-on | kit-off |
|---|---|---|
| **빈 화면 · 에러 · 로딩** | 세 화면 모두 세 상태를 채움 (셸이 강제) | 로딩·에러 처리 **없음** (r13 만 에러 타입 일부) |
| **화면 간 일관성** | 같은 앱 틀 · 제목 줄 · 면 · 간격 | 화면마다 자기 틀을 새로 짬 (제목 줄 · 옆 메뉴 · 여백이 제각각) |
| **제품 고유의 선택** | r03 강한 확인(이름 입력) — 카드가 정한 것 | 일반 확인창 — 딸린 기록을 적었지만 이름 입력은 없음 |
| **셸 선택** | r13 검토 대기열 | r13 목록 + 옆 상세 (경계 문장 — 둘 다 말이 된다) |
| **결정의 기록** | 명세에 셸 · 유형 · 근거 · 망설인 것 (6~8개) | 없음 — 왜 그렇게 했는지 코드 주석에만 일부 |
| **자동 검증** | 명세 + 경로로 시나리오가 돈다 | 돌릴 수 없다 (사람이 눌러 봐야 한다) |
| 코드 양 | 275 ~ 363줄 | 573 ~ 616줄 (틀을 매번 새로 짠다) |

## 해석

1. **키트의 값은 "옳은 UX 판단"보다 일관성 · 빠짐없음 · 기록 · 검증에 있다.** 에이전트는 일반적인 좋은 판단(되살릴 수 있으면 되돌리기)을 이미 한다.
   시험용 카드 대부분이 그런 일반 원칙이라, 카드가 판단을 바꾼 곳은 r03 의 강한 확인 하나뿐이었다.
2. **정책 카드는 "모델이 기본으로 하지 않을 제품의 선택"을 담을 때 값이 크다.** 강한 확인 · 행 동작 위치 · 저장 방식처럼 팀이 정해야 일관되는 것.
   일반 원칙만 담은 카드는 기록과 검증의 손잡이 역할은 하지만 결과를 바꾸지는 않는다.
3. **셸의 값은 상태 슬롯 강제와 틀의 통일이다.** 경계 문장에서 어느 셸을 고르는가는 "정답"보다 "팀의 약속"에 가깝다.
4. **토큰·부품만으로도 계약은 지켜진다** — 샌드박스 1차 결과와 같다. 바닥 층은 이미 제 몫을 한다.

## 다시 만들 때 쓸 것

- 셸: 상태 슬롯 강제는 유지. 틀 통일이 핵심이므로 셸마다 **잘 채운 예시**를 붙이거나 칸 안 규칙(필터 줄 배치, 표 열 순서)을 조금 더 두껍게.
- 정책: 일반 원칙은 AGENTS.md 한 줄로 줄이고, 카드는 **제품팀이 고른 것**(모델 기본과 다를 수 있는 것) 위주로.
- 명세·검증: 유지 — kit-off 에는 없는 "왜"의 기록과 자동 확인이 가장 분명한 차이다.

## 한계

세 문장 · 한 번씩 · 같은 모델. kit-off 도 같은 모델이라 "일반 원칙을 이미 안다"는 이 모델의 성질이다. 더 약한 모델이면 카드의 몫이 커질 수 있다.
