# 에이전트 파이프라인 시험 — 설계

> **상태: 시험용.** 셸 목록·정책 카드·메타 값은 시험이 끝나면 통째로 다시 만든다.
> 이 문서가 확정하는 것은 **틀**(폴더·형식·절차·검증)뿐이다.
> 브랜치 `에이전트-파이프라인-시험` 에서만 작업하고, 판정이 날 때까지 main 에 합치지 않는다.
> 1단계에서 바뀐 것과 그 이유: `presets/_시험/기록/1단계.md` · 2단계: `presets/_시험/기록/2단계.md`
> **배포 전에 반드시 볼 것은 12절**에 모아 두었다.

## 0. 무엇을 시험하나

요구사항 한 문장을 받은 에이전트가

1. 셸 목록에서 **맞는 페이지 셸을 고르고** (이웃 셸과 구분해서)
2. 정책 목록에서 **상황에 맞는 카드와 유형을 고르고** (결정표의 조건으로)
3. 그 셸·카드대로 **실제로 동작하는 화면을 만드는가**

를 **결과물**(코드·동작·화면)로 판정한다. 목데이터를 참조했는지가 아니라 나온 화면을 본다.

프리셋은 `saas` 하나로 고정한다. 색·밀도가 같으므로 차이는 전부 구조 차이다.

## 0-1. 원칙 — 어떤 요청이든 화면은 만든다 (2026-09-29 보강)

실사용자는 자기 요청이 "셸에 맞는지"를 알 수 없다. 그래서 파이프라인은 **요청에 따라 만들어지거나 안 만들어지는 일이 없어야 한다.**

| 경우 | 하는 일 |
|---|---|
| 맞는 셸이 있다 | 그 셸을 **최대한 따른다** |
| 셸 구조는 맞는데 요소를 더해야 한다 | 셸 + **확장 자리**(`lead` 본문 위 · `side` 오른쪽 칸) |
| 한 화면이 여러 셸을 오간다 | `셸` + `추가 셸` |
| 맞는 셸이 없다 | **자유 화면 셸 `free`** — 바깥 틀 · 면 · 간격 · 상태 칸은 같고 본문만 자유. 명세에 가장 가까운 셸 · 부족한 점을 남긴다(새 셸의 재료) |

어느 경우든 **문법(계약 토큰 · 부품 · 상시 규칙)은 같다.** 그래서 결과가 앱 안에서 튀지 않는다.
검사가 통과하지 못해도 화면은 남기고 이유를 `확인 필요` 에 적는다 — 검사는 막는 장치가 아니라 알리는 장치다.
(1~3단계에서 "맞는 셸이 없으면 멈춘다"를 썼던 것은 **선택을 제대로 하는지 재기 위한 시험 장치**였다. 파이프라인 검증이 끝나 풀었다.)

## 1. 남기는 것 / 갈아 끼우는 것

| 남긴다 (틀) | 갈아 끼운다 (내용) |
|---|---|
| 폴더 자리, 셸 메타 형식, 정책 카드 형식, 명세 형식 | 셸 종류와 각 셸의 레이아웃 |
| 생성 절차 (`SKILL.md`) | 정책 카드 문구, 갈래·유형 구성 |
| 목록 생성·검증 스크립트, 시나리오 실행기 | 메타 값, 채점표, 요구사항 세트 |

부품 패키지(`packages/*`), 토큰, `AGENTS.md` 는 **건드리지 않는다.** 구조를 버리게 되면 지울 것은
이 폴더와 브랜치뿐이다.

## 2. 폴더

```
presets/saas/
  설계.md             이 문서
  SKILL.md            에이전트가 따르는 화면 생성 절차
  index.json          셸·정책 목록 (스크립트가 생성, 손으로 고치지 않는다)
  frame/              앱 틀: 상단 메뉴 + 임시 왼쪽 메뉴
  shells/<id>/        shell.tsx (뼈대) + shell.json (메타)
  policy/<결정>/      _갈래.md (결정표 + 분류) + <유형>.md (카드)   — 폴더 하나 = 결정 하나
presets/_시험/        에이전트가 보지 않는 곳 (설치기가 샌드박스로 보내지 않는다)
  요구사항.json       시험 문장 (앞에 [id] 를 붙여 넣는다)
  채점표.json         요구사항별 정답 셸 · 허용 셸 · 핵심/금지 유형 · 정답 유형
  견본/               카드 검증용 화면 (카드 29장을 전부 덮는다) + 셸 견본
  견본-돌리기.mjs     견본으로 카드 시나리오가 통과하는지 확인
  채점.mjs            3단계 채점 (선택 · 동작 · 연 파일)
  시험-안내.md        직접 돌리는 법
  기록/               실행별 결과
scripts/agent-kit/    index 생성 · 명세/화면 검사 · 시나리오 실행기
```

## 3. 앱 틀과 임시 왼쪽 메뉴

- 앱 틀은 모든 화면이 공유하는 하나다. 시험 대상이 아니다.
- **왼쪽 메뉴(임시)** 는 부품 패키지에 넣지 않고 `frame/side-nav.tsx` 에 둔다.
  묶음 제목 = 메뉴 그룹 제목 모양, 항목 = 메뉴 항목 모양, 현재 위치 = 선택 면(`bg-surface-selected`),
  묶음 접기 = Collapsible. 계약 클래스만 쓴다. 진짜 부품이 생기면 이 파일만 바꾼다.

## 4. 페이지 셸

### 4-1. 형식

`shell.json`
```json
{
  "id": "list",
  "이름": "목록 관리",
  "쓰는 때": ["많은 행을 찾고 좁히고 한꺼번에 바꾼다"],
  "쓰지 않는 때": [{ "이웃": "list-detail", "차이": "한 건을 보면서 옆에서 바로 처리해야 하면 저쪽" }],
  "슬롯": {
    "제목줄": { "필수": true },
    "필터": { "필수": true },
    "본문": { "필수": true },
    "빈 상태": { "필수": true, "상태": true },
    "에러": { "필수": true, "상태": true },
    "로딩": { "필수": true, "상태": true }
  },
  "부품": ["Table", "Select", "Menu", "Badge"],
  "최소 데이터": "행 8개 이상"
}
```

`shell.tsx` — 슬롯을 props 로 받는 레이아웃. **상태 슬롯**(빈·에러·로딩·완료 피드백)의 타입은
`ReactNode | { 없음: string }` 이다. 빼먹으면 타입 검사가 막고, 해당이 없으면 이유를 적어야 통과한다.

### 4-1-1. 셸 형식에 더한 것 (2026-09-29 보강)

- **확장 자리** — 모든 셸에 `lead`(본문 위 한 줄). 오른쪽 칸이 없는 셸 10종(list · gallery · board · settings · permission-matrix · report · compare · search · import · inbox)에 `side`.
  공통 부품 `Extended` 가 그린다 — 칸 안에 억지로 끼우지 않게, 화면마다 같은 자리 · 같은 간격이 되게.
- **`예비: true`** — 목록의 일반 셸에서 빼고 `맞는 셸이 없을 때` 로 따로 싣는다 (지금은 `free` 하나).
- **`예시`** — `shell.json` 에 `"예시": "example.tsx"` 를 두면 목록에 경로가 실리고, 절차가 "고른 셸에 예시가 있으면 연다"로 읽는다.
  칸 안의 모양(필터 줄 배치 · 표 열 순서)을 맞추는 기준이다. **지금은 비어 있다** — 셸을 다시 만들 때 채운다 (kit-off 비교에서 칸 안이 흔들린다는 것이 보였다).

### 4-2. 시험용 목록 (20종 + 자유 화면)

헷갈릴 만한 **이웃**을 일부러 넣었다. 이웃 구분이 이 시험의 핵심이다.

| 계열 | id | 이름 | 주로 헷갈리는 이웃 |
|---|---|---|---|
| 목록 | `list` | 목록 관리 | list-detail, report |
| | `list-detail` | 목록 + 옆 상세 | list, review-queue, inbox |
| | `gallery` | 카드 격자 | list |
| | `tree-list` | 왼쪽 트리 + 목록 | list, settings |
| | `board` | 상태별 열 보드 (끌기 없음) | list |
| 상세 | `detail` | 상세 (제목·탭·옆 정보) | detail-activity |
| | `detail-activity` | 활동 이력 중심 상세 | detail, inbox |
| | `compare` | 두 항목 나란히 비교 | detail |
| 입력 | `form` | 전체 페이지 폼 | wizard, settings |
| | `wizard` | 단계형 입력 | form, import |
| | `grid-edit` | 표에서 바로 고치기 | list, form |
| | `settings` | 하위 메뉴 + 구역별 설정 | form, tree-list |
| | `permission-matrix` | 역할 × 권한 체크 표 | grid-edit, settings |
| 요약 | `dashboard` | 요약 카드 + 최근 목록 | report |
| | `report` | 기간 필터 + 수치 + 표 + 내보내기 | dashboard, list |
| 처리 | `review-queue` | 한 건씩 승인·반려 | list-detail, inbox |
| | `import` | 업로드 → 검증 결과 → 확정 | wizard |
| | `inbox` | 알림·받은함 | list-detail, review-queue |
| 기타 | `onboarding` | 첫 사용 (빈 상태 + 할 일 목록) | dashboard |
| | `search` | 전역 검색 결과 (유형별 묶음) | list |

**셸이 없는 요구**(시험에서 "맞는 셸 없음"을 말해야 하는 것): 일정 캘린더, 실시간 채팅, 차트 분석, 지도.

## 5. UX 정책

### 5-1. 무엇이 정책인가

**부품으로는 두 방식이 다 되는데 제품이 하나로 정해야 하는 것.**
어떻게 여는지 = 부품 문서, 어디에 놓는지 = 셸, 어느 방식으로 할지 = 정책.

항상 필요한 규칙(빈 상태·필드 에러·확인 후 삭제의 원칙 …)은 **AGENTS.md 에 그대로** 두고,
상황에 따라 필요한 것만 카드로 만든다.

### 5-2. 분류: 결정 > 유형 (두 단계까지만)

**폴더 하나 = 결정 하나**(필터 적용 · 결과 나누기 · 삭제 · 저장 방식 …). 결정 안의 유형은 **결정표**(`_갈래.md`)의 한 줄이다.
유형을 늘리려면 카드 한 장 + 결정표 한 줄. 결정을 늘리려면 폴더 하나.
사용자 행동 일곱 가지(**조회 · 선택 · 입력 · 삭제 · 피드백 · 이동 · 표시**)는 `_갈래.md` 의 `분류` 칸으로 남는다 — 목록을 묶는 표시일 뿐 층이 아니다.
(2단계에서 바꿈: "조회" 하나 안에 *필터를 어떻게 적용할지*와 *결과를 어떻게 나눌지*처럼 **독립된 결정이 여럿**이라,
행동 하나를 폴더로 두면 "유형 하나만 고른다"가 성립하지 않았다.)
한 화면에서 유형을 둘 이상 써도 되는 결정은 `_갈래.md` 에 `여럿 가능: true` (결과 알림: 성공 토스트 + 실패 화면 안 알림).

결정표 규칙
- 왼쪽 칸(조건)은 요구사항에서 **사실로 확인할 수 있는 것**만 쓴다 (되돌릴 수 있는가, 영향이 어디까지인가, 몇 건인가).
  "중요하면" 같은 해석이 갈리는 말은 쓰지 않는다.
- **기본값 줄이 반드시 있다.** 요구사항에 정보가 없으면 기본값을 쓰고 명세의 `확인 필요` 에 남긴다.
- 유형이 더 갈라져야 하면 층을 늘리지 않고 유형을 하나 더 만든다.

예 — 삭제
| 조건 | 유형 |
|---|---|
| 되돌릴 수 있다 | `즉시-되돌리기` |
| 되돌릴 수 없고 그 항목에 그친다 | `확인` (기본값) |
| 되돌릴 수 없고 다른 데이터까지 지워진다 | `강한-확인` |

### 5-2-1. 무엇을 카드로 두나 (kit-off 비교에서 정함)

키트 없이도 에이전트는 **일반적인 좋은 판단**(되살릴 수 있으면 되돌리기, 성공은 토스트)을 이미 한다. 그런 카드는 결과를 바꾸지 않았다.
결과를 바꾼 것은 **제품이 따로 정한 선택**(이름을 입력하는 강한 확인)뿐이었다. 그래서 다시 만들 때:

| 둔다 | 줄인다 |
|---|---|
| 모델의 기본과 **다를 수 있는** 제품의 선택 (강한 확인 · 행 동작 위치 · 저장 방식 · 확인 문구) | 누구나 아는 일반 원칙 → AGENTS.md 한 줄 |
| 화면끼리 **같아야** 뜻이 있는 것 (배지 색의 뜻 · 쪽 나눔 방식) | 한 화면 안에서만 의미 있는 세부 |
| 에이전트가 **빠뜨리는** 것 (상태 칸 — 이건 셸이 강제한다) | |

카드가 결과를 바꾸지 않더라도 **기록과 검증의 손잡이**(명세에 왜 그랬는지 · 시나리오)는 남는다 — kit-off 에는 그것이 없다.

### 5-3. 카드 형식

```md
---
id: delete-confirm
갈래: 삭제
유형: 확인
조건: 되돌릴 수 없고 영향이 그 항목에 그친다
기본: true
강도: 필수            # 필수 | 권장 (권장은 이유를 명세에 적으면 어길 수 있다)
종류: 결과 보장        # 결과 보장 | 경로 제약 (경로 제약은 드물게)
적용 셸: [전부]        # 또는 [list, list-detail]. 같은 상황에서 셸 한정 카드가 이긴다
부품: [AlertDialog, AlertDialogConfirmFooter, Toast]
보장:
  - 확정하기 전까지 대상이 남아 있다
  - 취소하면 아무것도 바뀌지 않는다
  - 확정하면 대상이 사라지고 결과를 알린다
검사: 시나리오          # 스크립트 | 시나리오 | 스크린샷
---
# 되돌릴 수 없는 것을 하나 지울 때

규칙: …
금지: …
이유: …
예시: (짧은 코드 조각)
```

- 제목은 **상황 문장**으로 쓴다. 요구사항과 말이 닮아야 찾힌다.
- 연결은 **카드 쪽에만** 적는다(`적용 셸`). 셸 메타에는 정책을 적지 않는다.
- **보장은 결과만** 적는다. 어디서 시작하는지·무엇으로 확인하는지는 적지 않는다(설계 제약이 되므로).
  느슨함의 기준: ① 화면을 두 가지 이상으로 짤 수 있고 ② 어떻게 짰든 참/거짓을 판정할 수 있다.
- **경로 제약**("삭제는 행 메뉴에서만" 처럼 제품이 경로 자체를 정하는 것)은 따로 표시하고 드물게 쓴다.

시험용 규모(2단계 실제): 분류 7 · 결정 13 · 카드 29. 경로 제약 2장(행 동작 위치).

**카드 단계 어휘**(시나리오): 기억 · 기억글자 · 누르기 · 보인다 · 안보인다 · 개수(차이 | 달라짐 | 늘어남 | 같음) · 글자(포함 | 달라짐 | 그대로) ·
값 · 입력 · 떠나기 · 막힘없음 · 비활성 · 활성 · 바쁨 · 기다리기 · 다시열기 · 실패로열기. 경로에서 값을 가져올 때는 `{ "경로": "이름" }`.

## 6. 명세 (에이전트가 구현 전에 쓰는 것)

`명세.json` (2026-09-29 보강: `추가 셸` · `실패 흉내`, free 일 때 `셸.가장 가까운` · `셸.부족한 점`)
```json
{
  "요구 요약": "",
  "주소": "#/<화면-id>",
  "데이터": { "필드": [], "목데이터": "행 몇 개" },
  "셸": { "id": "", "이유": "", "제외한 이웃": [{ "id": "", "이유": "" }] },
  "슬롯": { "빈 상태": "무엇을 보이는가 | { 없음: 이유 }" },
  "정책": [{ "id": "", "근거 조건": "요구사항의 어느 사실 때문에" }],
  "경로": { "delete-confirm": { "시작": [{ "역할": "button", "이름": "더보기" }, { "역할": "menuitem", "이름": "삭제" }], "확인창": { "역할": "alertdialog" }, "…": "카드 단계가 쓰는 이름마다" } },
  "확인 필요": []
}
```

**경로**는 카드가 아니라 에이전트가 적는다. 카드 = 무엇을 보장하나, 명세 = 어떻게 했나,
실행기 = 명세의 방법이 카드의 보장을 지키는지 본다. 적은 경로와 화면이 다르면 그것도 실패다.
요소는 **역할과 이름**으로 가리킨다(클래스·테스트 ID 금지) — 어떻게 짰든 같은 검사가 통한다.
경로 이름(대상·시작·확인창·확정·취소·결과·되돌리기 …)은 **카드가 짓는다.** 검사기가 카드 단계에서 필요한 이름을 뽑아 명세와 대조한다.

**요소 가리키기:** `{ "역할", "이름", "순번", "안" }` 또는 역할이 없는 요소는 `{ "글자", "안" }`. 목록 항목(`listitem`)은 안의 글자가
이름이 되지 않으므로 글자로 가리킨다(2단계에서 발견 — 이름으로 쓰면 "안보인다"가 가짜로 통과한다. 검사기가 막는다).
경로 한 칸에 `"입력": "…"` 이 있으면 누르지 않고 그 글자를 넣는다(검색칸으로 조건 바꾸기).
**준비:** 보장이 어떤 상태에서만 보이면 그 카드 경로에 `준비`(먼저 누를 것)를 적는다.
**실패 흉내:** 실패할 수 있는 동작은 `useShellFail()` 로 감싸고 명세 `실패 흉내` 에 이름을 적는다. 실행기가 `?fail=<이름>` 으로 연다.

**상태 스위치:** 셸은 `state` 를 받고, 화면은 계산한 상태를 `useShellState()` 에 거쳐 넘긴다.
실행기가 주소에 `?state=empty|error|loading` 을 붙여 상태 슬롯을 하나씩 띄워 본다.
**목데이터**는 화면 폴더의 `data.ts` 에 두고 첫 줄에 린트 제외 표시를 한다(클래스는 쓰지 않는다).

## 7. 절차 (`SKILL.md`)

1. `index.json` 을 읽는다 — 셸과 카드의 **제목·조건만** 있다
2. 셸을 고른다. 이웃과 비교해 제외 이유를 적는다. 요소를 더하면 확장 자리, 맞는 셸이 없으면 **`free` 로 짓는다** (멈추지 않는다)
3. 요구사항에 해당하는 **갈래마다 결정표로 유형 하나**를 고른다 (1단계에서 고침 — "필수 카드는 전부 따라온다"는
   유형 갈래와 충돌했다. `강도` 는 "어길 수 있는가"만 뜻한다)
4. 고른 셸·카드 파일만 연다 → 명세를 쓴다
5. 구현한다
6. 검사 스크립트를 돌리고 고친다

## 8. 검증

| 겹 | 보는 것 | 방법 |
|---|---|---|
| 정적 | 계약 위반 0 · 명세 칸 다 채움 · 명세의 셸 = 실제로 쓴 셸 · 카드의 부품 사용 · 경로 제약 준수 | 스크립트 |
| 동작 | 카드의 보장이 명세의 경로에서 지켜지는가 | 시나리오 실행기 (브라우저 자동 조작, 샌드박스에만 설치) |
| 시각 | 셸 구조가 살아 있는가 | 스크린샷 검토 |
| 선택 | 정답 셸·정답 유형을 골랐는가, 어떤 파일을 열었는가 | 채점표 + 세션 기록 (`채점.mjs`) |
| 카드 | 카드의 시나리오가 **맞게 만든 화면**에서 통과하는가 — 본 시험 전에 카드 결함을 지운다 | 견본 10개 (`견본-돌리기.mjs`) |

동작 검사는 **채점표의 정답 유형**으로 돌린다. 유형을 잘못 고르면 동작에서 드러난다.

## 10. 판정 — 시험 전에 확정

실패마다 하나로 분류한다.

- **내용 결함** → 카드·메타를 고친다, 틀 유지: 문장이 모호함, 조건이 겹침, 이웃 차이가 안 적힘
- **구조 결함** → 틀을 다시 짠다, 아래 중 하나라도
  1. 내용을 고쳐도 같은 실패가 반복된다
  2. 필요한 정보를 적을 자리가 형식에 없다
  3. 카드가 명확한데 에이전트가 목록에서 찾지 못한다
  4. 검증이 성공과 실패를 가려내지 못한다

## 13. 4단계 — 현실 사용 시나리오 (다음 시험의 방향)

1~3단계는 **파이프라인의 정합성**(고르는가 · 따르는가 · 검사가 가려내는가)을 쟀다. 판정: 구조 결함 없음 (기록/3단계/판정-1차 · 2차).
다음은 **실사용에 가까운 조건**에서 "무엇이든 일관되게 나오는가"를 본다. 바뀌는 것:

| | 1~3단계 | 4단계 |
|---|---|---|
| 문장 | 셸에 맞춰 조건을 심음 | 실제 요청처럼 — 셸에 없는 화면 · 요소를 더하는 요청 · 모호한 요청 섞기 |
| 맞는 셸이 없을 때 | 멈추면 정답 | **free 로 지으면 정답** (멈추면 옛 규칙) |
| 판정의 무게 | 셸 · 유형을 맞혔나 | 화면이 나왔나 · 틀 · 상태 칸 · 계약 위반 0 · 화면끼리 일관한가(사진) · 확장 자리를 썼나 |
| 검사 실패 | 고칠 때까지 | 알리고 남긴다 (`확인 필요`) |
| 정답 셸이 여럿일 수 있음 | 허용 목록 | 허용을 넓힌다 — "팀의 약속"에 가까운 경계는 둘 다 인정 |

시작 시점: **셸 · 정책을 다시 만든 뒤.** 지금 셸 · 카드는 임시라, 현실 시나리오의 흔들림이 임시 내용 탓인지 가를 수 없다.
그 전까지는 지금 시험 세트(명확 · 경계 · 없음 · 확장 18문장)로 틀 보강이 먹히는지만 본다.
